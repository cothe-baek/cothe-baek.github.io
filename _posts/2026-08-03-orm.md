이번에는 데이터를 MySQL에 영구 저장하고, FastAPI와 MySQL 사이의 데이터 처리를 SQLAlchemy가 담당하도록 변경할 예정

```text
FastAPI
→ SQLAlchemy
→ PyMySQL
→ MySQL
```

이번 학습 핵심 포인트

* ORM이 테이블과 Python 객체를 어떻게 연결하는지
* SQLAlchemy의 Engine, Model, Session이 각각 어떤 역할을 하는지
* 객체를 생성하거나 수정했을 때 SQL이 언제 실행되는지
* Session과 트랜잭션이 어떻게 관리되는지

## 1. ORM (Object Relational Mapping)

ORM은 관계형 데이터베이스의 테이블 구조를 Python의 클래스와 객체로 표현하는 방식임.

| 관계형 데이터베이스 | Python ORM  |
| ---------- | ----------- |
| 테이블        | 클래스         |
| 행 또는 레코드   | 객체          |
| 컬럼         | 객체의 속성      |
| 기본 키       | 객체를 식별하는 속성 |
| 외래 키       | 다른 객체와의 관계  |

예를 들어 MySQL에 다음과 같은 `tasks` 테이블이 있다고 가정하면

| id | title           | description | completed |
| -: | --------------- | ----------- | --------- |
|  1 | FastAPI 공부하기    | CRUD 구현     | false     |
|  2 | SQLAlchemy 공부하기 | ORM 이해      | true      |

SQLAlchemy ORM에서는 해당 테이블을 `Task` 클래스로 표현함

```text
tasks 테이블                 Task 클래스
────────────────────────────────────────
id 컬럼                ↔      task.id
title 컬럼             ↔      task.title
description 컬럼       ↔      task.description
completed 컬럼         ↔      task.completed
테이블의 한 행         ↔      Task 객체 하나
```

따라서 다음 객체는 `tasks` 테이블의 한 행에 대응함

```python
task = Task(
    title="SQLAlchemy 공부하기",
    description="ORM 구조 이해",
    completed=False,
)
```

이 객체를 Session에 추가하고 저장하면 SQLAlchemy가 필요한 `INSERT` 문을 생성해 MySQL에 전달함

### ORM을 사용하는 이유

ORM을 사용하면 Python 객체를 중심으로 같은 작업을 표현할 수 있음

```python
task = Task(
    title="SQLAlchemy 공부하기",
    description="ORM 구조 이해",
)

db.add(task)
db.commit()
```

ORM은 SQL을 대체하는 기술이라기보다, SQL 작업을 Python 객체 중심으로 다룰 수 있도록 추상화하는 기술임.

## 2. SQLAlchemy의 전체 구조

SQLAlchemy는 크게 **ORM 계층**과 **Core 계층**으로 구성됨.

```text
FastAPI
  ↓
SQLAlchemy ORM
  - 클래스와 테이블 매핑
  - ORM 객체 상태 관리
  - Session
  - 객체 간 관계 관리
  ↓
SQLAlchemy Core
  - SQL 문 생성
  - 데이터베이스 연결 관리
  - 트랜잭션 관리
  - Connection Pool
  - DBMS별 SQL 차이 처리
  ↓
DBAPI Driver
  - PyMySQL
  ↓
MySQL
```

### SQLAlchemy ORM

Python 클래스와 데이터베이스 테이블을 연결하는 상위 계층임.

다음 기능을 담당함.

| 기능           | 설명                        |
| ------------ | ------------------------- |
| 객체-테이블 매핑    | Python 클래스와 DB 테이블을 연결함   |
| 객체 상태 추적     | 객체가 생성·수정·삭제되었는지 관리함      |
| Unit of Work | 객체의 변경사항을 모아 필요한 SQL을 결정함 |
| Identity Map | 같은 행을 하나의 Python 객체로 관리함  |
| Relationship | 테이블 간 관계를 객체 관계로 표현함      |

### SQLAlchemy Core

ORM 아래에서 실제 SQL과 데이터베이스 연결을 처리하는 기반 계층임.

다음 기능을 담당함.

| 기능              | 설명                                          |
| --------------- | ------------------------------------------- |
| SQL 생성          | `SELECT`, `INSERT`, `UPDATE`, `DELETE` 문 생성 |
| Engine          | 데이터베이스 접근 설정 관리                             |
| Connection      | 실제 데이터베이스 연결 사용                             |
| Transaction     | 여러 SQL을 하나의 작업 단위로 관리                       |
| Connection Pool | 데이터베이스 연결 재사용                               |
| Dialect         | MySQL, PostgreSQL 등 DBMS별 차이 처리             |

ORM은 독립적으로 동작하는 것이 아니라 SQLAlchemy Core 위에서 동작함.

## 3. Engine, Dialect, Driver

SQLAlchemy가 데이터베이스에 접근하려면 Engine, Dialect, Driver가 필요함.

```text
SQLAlchemy ORM
→ Engine
→ Dialect
→ Driver
→ MySQL
```

### Engine

Engine은 데이터베이스에 접근하기 위한 중심 객체임.

주요 역할은 다음과 같음.

* 데이터베이스 접속 정보 보관
* Connection Pool 관리
* 데이터베이스 연결 생성
* Dialect와 Driver 연결
* SQL 실행을 데이터베이스에 전달

Engine은 일반적으로 애플리케이션이 실행될 때 한 번 생성하고 계속 재사용함.

```python
engine = create_engine(DATABASE_URL)
```

Engine 자체가 하나의 데이터베이스 연결을 의미하는 것은 아님.

```text
Engine
→ 필요한 시점에 Connection을 빌려줌
→ 작업이 끝나면 Connection을 Pool에 반환함
```

### Database URL

SQLAlchemy는 URL 형식으로 데이터베이스 접속 정보를 전달받음.

```text
DBMS+Driver://사용자:비밀번호@호스트:포트/데이터베이스
```

MySQL과 PyMySQL을 사용하는 경우의 예시는 다음과 같음.

```text
mysql+pymysql://root:password@127.0.0.1:3306/task_db
```

| 구성       | 값           | 의미                       |
| -------- | ----------- | ------------------------ |
| DBMS     | `mysql`     | 사용할 데이터베이스               |
| Driver   | `pymysql`   | Python과 MySQL을 연결할 라이브러리 |
| 사용자      | `root`      | MySQL 사용자                |
| 비밀번호     | `password`  | 사용자 비밀번호                 |
| Host     | `127.0.0.1` | MySQL 서버 주소              |
| Port     | `3306`      | MySQL 포트                 |
| Database | `task_db`   | 사용할 데이터베이스 이름            |

실제 프로젝트에서는 비밀번호를 코드에 직접 작성하지 않고 환경변수나 `.env` 파일로 분리함.

### Dialect

Dialect는 데이터베이스 종류별 SQL 차이를 처리함.

MySQL, PostgreSQL, SQLite는 모두 SQL을 사용하지만 다음과 같은 부분에서 차이가 있을 수 있음.

* 데이터 타입
* 자동 증가 방식
* 날짜 및 시간 처리
* 문자열 처리
* 지원하는 SQL 문법
* `RETURNING` 지원 여부
* 데이터베이스 함수

개발자가 SQLAlchemy 공통 표현을 사용하면 Dialect가 해당 DBMS에 맞는 SQL을 생성함.

```text
SQLAlchemy 표현
→ MySQL Dialect
→ MySQL용 SQL
```

### Driver

Driver는 Python 프로그램과 데이터베이스가 실제로 통신할 수 있도록 하는 라이브러리임.

이번 실습에서 사용하는 Driver는 PyMySQL임.

```text
SQLAlchemy
→ PyMySQL
→ MySQL
```

`mysql+pymysql`에서 `mysql`은 Dialect, `pymysql`은 Driver를 의미함.

### Connection Pool

데이터베이스 연결을 생성하는 작업에는 비용이 발생함.

요청이 들어올 때마다 새로운 연결을 생성하고 제거하면 성능이 저하될 수 있음.

Connection Pool은 생성된 연결을 보관했다가 다음 요청에서 재사용함.

```text
요청 A
→ Pool에서 Connection 대여
→ SQL 실행
→ Connection 반환

요청 B
→ 기존 Connection 재사용
```

Connection Pool은 기본적으로 Engine이 관리함.

## 4. ORM Model

ORM Model은 데이터베이스 테이블과 연결되는 Python 클래스임.

SQLAlchemy 2.x에서는 `DeclarativeBase`, `Mapped`, `mapped_column()`을 이용해 모델을 선언함.

### Base 클래스

모든 ORM Model이 공통으로 상속할 기반 클래스를 정의함.

```python
class Base(DeclarativeBase):
    pass
```

`Base`는 다음 정보를 관리함.

* 등록된 ORM Model
* 테이블 이름
* 컬럼 구조
* 기본 키와 외래 키
* 테이블 간 관계
* 전체 데이터베이스 스키마 정보

각 모델은 `Base`를 상속함.

```python
class Task(Base):
    ...
```

### 테이블과 클래스 연결

```python
class Task(Base):
    __tablename__ = "tasks"
```

`__tablename__`은 해당 클래스가 연결될 데이터베이스 테이블 이름을 의미함.

```text
Python 클래스: Task
데이터베이스 테이블: tasks
```

### Mapped

`Mapped`는 SQLAlchemy가 관리하는 ORM 속성이라는 의미임.

```python
id: Mapped[int]
title: Mapped[str]
description: Mapped[str | None]
```

`Mapped[int]`는 Python 코드에서 해당 속성을 `int`로 다룬다는 의미임.

```python
task.id
```

`Mapped[str | None]`은 문자열 또는 `None`을 허용한다는 의미임.

```python
task.description
```

### mapped_column

`mapped_column()`은 데이터베이스 컬럼의 세부 설정을 정의함.

```python
id: Mapped[int] = mapped_column(
    primary_key=True,
    autoincrement=True,
)
```

대표 설정은 다음과 같음.

| 설정                   | 의미           |
| -------------------- | ------------ |
| `primary_key=True`   | 기본 키 지정      |
| `autoincrement=True` | 값 자동 증가      |
| `nullable=False`     | NULL 허용 안 함  |
| `nullable=True`      | NULL 허용      |
| `unique=True`        | 중복 값 허용 안 함  |
| `index=True`         | 인덱스 생성       |
| `default=값`          | Python 측 기본값 |
| `server_default=값`   | 데이터베이스 측 기본값 |
| `ForeignKey()`       | 외래 키 설정      |

ORM Model은 단순히 응답 형태를 정의하는 클래스가 아니라 실제 데이터베이스 구조와 연결되는 클래스임.

## 5. MetaData와 테이블 생성

`Base`에는 등록된 모든 테이블의 구조 정보가 저장됨.

```python
Base.metadata
```

예를 들어 `Task` 모델을 등록하면 MetaData에는 다음과 같은 정보가 포함됨.

```text
tasks 테이블
├── id: 정수, 기본 키, 자동 증가
├── title: 문자열, NULL 불가
├── description: 문자열, NULL 허용
└── completed: 불리언, NULL 불가
```

다음 코드는 등록된 모델을 기준으로 존재하지 않는 테이블을 생성함.

```python
Base.metadata.create_all(bind=engine)
```

처리 흐름은 다음과 같음.

```text
ORM Model 등록
→ Base.metadata에 테이블 정보 저장
→ create_all() 실행
→ MySQL에 테이블 존재 여부 확인
→ 테이블이 없으면 CREATE TABLE 실행
```

`create_all()`은 초기 실습에서는 편리하지만 기존 테이블 구조를 변경하는 migration 도구는 아님.

예를 들어 이미 만들어진 `tasks` 테이블에 새로운 컬럼을 모델에 추가하더라도 기존 테이블이 자동으로 안전하게 변경되는 것은 아님.

```text
처음 테이블 생성
→ create_all()

운영 중 테이블 구조 변경
→ Alembic migration
```

## 6. Session과 트랜잭션

Session은 SQLAlchemy ORM에서 가장 중요한 구성요소 중 하나임.

Session은 단순한 데이터베이스 연결 객체가 아니라 다음 내용을 함께 관리함.

* ORM 객체 조회
* 새 객체 등록
* 객체 변경 감지
* 객체 삭제
* SQL 실행
* 트랜잭션
* commit과 rollback
* 동일한 행에 대응하는 객체 관리

```text
ORM 객체 생성 또는 조회
→ Session이 객체 상태 관리
→ 필요한 SQL 결정
→ Engine에서 Connection 대여
→ SQL 실행
→ commit 또는 rollback
```

### Session과 Connection의 차이

| 구분          | 역할                        |
| ----------- | ------------------------- |
| Session     | ORM 객체와 트랜잭션을 관리함         |
| Connection  | 데이터베이스와 실제로 통신하는 연결임      |
| Engine      | Connection을 만들고 Pool을 관리함 |
| Transaction | 여러 SQL을 하나의 작업 단위로 묶음     |

Session을 사용한다고 Session 자체가 MySQL 연결 하나가 되는 것은 아님.

```text
Session
→ Engine에 Connection 요청
→ Connection Pool에서 연결 대여
→ SQL 실행
→ 트랜잭션 종료
→ Connection 반환
```

### 주요 Session 메서드

| 메서드          | 역할                       |
| ------------ | ------------------------ |
| `add()`      | 새 객체를 저장 대상으로 등록함        |
| `get()`      | 기본 키로 객체를 조회함            |
| `execute()`  | SQL 문을 실행하고 행 단위 결과를 반환함 |
| `scalars()`  | 결과에서 ORM 객체 또는 단일 값을 추출함 |
| `delete()`   | 객체를 삭제 대상으로 등록함          |
| `flush()`    | 변경사항을 SQL로 데이터베이스에 전달함   |
| `commit()`   | 현재 트랜잭션을 확정함             |
| `rollback()` | 현재 트랜잭션의 변경사항을 취소함       |
| `refresh()`  | 데이터베이스 값을 객체에 다시 반영함     |
| `close()`    | Session이 사용한 자원을 정리함     |

### add, flush, commit 차이

세 메서드는 역할이 다름.

```python
db.add(task)
```

`add()`는 객체를 Session에 등록함.

```text
이 객체는 새 데이터임
→ 이후 INSERT가 필요함
```

이 시점에는 실제 `INSERT`가 실행되지 않았을 수 있음.

```python
db.flush()
```

`flush()`는 Session이 관리하던 변경사항을 SQL로 만들어 데이터베이스에 전달함.

```text
새 객체
→ INSERT

변경된 객체
→ UPDATE

삭제 대상 객체
→ DELETE
```

하지만 flush만 실행한 상태에서는 트랜잭션이 아직 확정되지 않음.

```text
flush
→ SQL 실행됨
→ 아직 rollback 가능함
```

```python
db.commit()
```

`commit()`은 현재 트랜잭션을 최종 확정함.

```text
flush
→ INSERT, UPDATE, DELETE 실행
→ COMMIT
→ 변경사항 확정
```

일반적으로 `commit()`을 실행하면 필요한 flush가 먼저 자동으로 수행됨.

### rollback

데이터베이스 작업 중 오류가 발생하면 현재 트랜잭션을 취소해야 함.

```python
try:
    db.add(task)
    db.commit()

except Exception:
    db.rollback()
    raise
```

`rollback()`은 commit되기 전 현재 트랜잭션에서 수행된 변경사항을 되돌림.

이미 성공적으로 commit된 이전 트랜잭션까지 되돌리는 것은 아님.

### refresh

```python
db.refresh(task)
```

`refresh()`는 데이터베이스의 현재 값을 다시 조회해 ORM 객체에 반영함.

주로 데이터베이스가 생성한 값을 가져올 때 사용함.

```text
Task 객체 생성
→ INSERT 실행
→ MySQL이 AUTO_INCREMENT id 생성
→ refresh()
→ 생성된 id를 Task 객체에 반영
```

## 7. ORM 객체의 상태

ORM 객체는 Session과의 관계에 따라 상태가 변함.

```text
Transient
→ Pending
→ Persistent
→ Detached
```

### Transient

일반 Python 객체만 생성된 상태임.

```python
task = Task(
    title="SQLAlchemy 공부하기",
)
```

```text
Python 메모리에는 존재함
Session에는 등록되지 않음
데이터베이스에는 저장되지 않음
```

### Pending

`add()`를 통해 Session에 등록된 상태임.

```python
db.add(task)
```

Session은 해당 객체가 새로운 데이터라는 사실을 알고 있음.

```text
Session에 등록됨
→ 다음 flush에서 INSERT 예정
```

### Persistent

flush가 실행되어 데이터베이스 행과 연결된 상태임.

```python
db.flush()
```

INSERT가 실행되어 데이터베이스의 특정 행과 연결되지만, commit 전이라면 트랜잭션은 아직 확정되지 않음.

### Deleted

`delete()`를 통해 삭제 대상으로 등록된 상태임.

```python
db.delete(task)
```

다음 flush에서 `DELETE`가 실행됨.

### Detached

Session이 닫히거나 객체가 Session에서 분리된 상태임.

```python
db.close()
```

객체는 Python 메모리에 남아 있을 수 있지만 더 이상 해당 Session이 관리하지 않음.

지연 로딩이 필요한 속성에 접근하거나 데이터베이스에서 값을 다시 불러오려 하면 문제가 발생할 수 있음.

## 8. Unit of Work와 변경 감지

SQLAlchemy Session은 **Unit of Work** 방식으로 동작함.

Unit of Work는 객체의 변경사항을 추적한 뒤 데이터베이스에 필요한 SQL을 결정하는 방식임.

예를 들어 다음과 같이 Task 객체의 속성을 변경했다고 가정함.

```python
task = db.get(Task, 1)
task.completed = True
```

개발자는 `UPDATE` SQL을 직접 작성하지 않았음.

하지만 Session은 처음 조회한 값과 현재 객체 값을 비교해 변경 사실을 추적함.

```text
기존 상태
completed = False

변경 상태
completed = True
```

이후 commit을 실행하면 SQLAlchemy가 다음과 같은 `UPDATE`를 생성함.

```sql
UPDATE tasks
SET completed = TRUE
WHERE id = 1;
```

```text
ORM 객체 속성 변경
→ Session이 변경 감지
→ flush 시 UPDATE 생성
→ commit으로 변경 확정
```

이것이 ORM 코드에서 단순히 속성을 변경하고 commit하는 것만으로 데이터베이스 수정이 가능한 이유임.

## 9. Identity Map

Session은 같은 기본 키를 가진 데이터베이스 행을 하나의 Python 객체로 관리함.

```python
task1 = db.get(Task, 1)
task2 = db.get(Task, 1)
```

같은 Session 안에서는 일반적으로 두 변수가 같은 객체를 가리킴.

```python
task1 is task2
```

```text
tasks 테이블의 id=1 행
→ 현재 Session 내부의 Task 객체 하나
```

이를 **Identity Map**이라고 함.

Identity Map을 사용하면 같은 데이터베이스 행이 서로 다른 Python 객체로 중복 관리되어 값이 충돌하는 문제를 줄일 수 있음.

다만 Identity Map은 모든 SELECT 결과를 저장하는 일반적인 쿼리 캐시는 아님.

## 10. SQLAlchemy 2.x 조회 방식

SQLAlchemy 2.x에서는 `select()`로 조회 문을 구성하고 Session을 통해 실행함.

### select

```python
stmt = select(Task)
```

`select()`는 실행할 SELECT 문을 만드는 단계임.

이 코드만으로 데이터베이스에 SQL이 실행되지는 않음.

```text
select(Task)
→ SELECT 문 객체 생성
→ 아직 DB 조회는 실행되지 않음
```

### where

조회 조건은 `where()`로 추가함.

```python
stmt = select(Task).where(
    Task.completed == True
)
```

다음 SQL과 유사한 문장이 생성됨.

```sql
SELECT *
FROM tasks
WHERE completed = TRUE;
```

### order_by

정렬 조건은 `order_by()`로 추가함.

```python
stmt = select(Task).order_by(
    Task.id
)
```

### execute

```python
result = db.execute(stmt)
```

`execute()`는 SQL을 실행하고 행 단위 결과를 반환함.

`select(Task)`를 실행한 경우 각 결과 행 안에 `Task` 객체가 들어 있는 형태가 될 수 있음.

### scalars

```python
tasks = db.scalars(stmt).all()
```

`scalars()`는 결과 행에서 첫 번째 값만 추출함.

ORM 객체를 조회할 때는 첫 번째 값이 `Task` 객체이므로 다음과 같은 리스트를 얻을 수 있음.

```text
[
    Task(id=1, ...),
    Task(id=2, ...)
]
```

### get

기본 키로 객체 하나를 조회할 때는 `Session.get()`을 사용할 수 있음.

```python
task = db.get(Task, 1)
```

```text
Task 테이블에서 기본 키가 1인 객체 조회
```

현재 Session의 Identity Map에 해당 객체가 이미 존재하면 추가 SELECT 없이 기존 객체를 반환할 수도 있음.

### 조회 방식 비교

| 방식                     | 용도                       |
| ---------------------- | ------------------------ |
| `select(Task)`         | SELECT 문 구성              |
| `where()`              | 조회 조건 추가                 |
| `order_by()`           | 정렬 조건 추가                 |
| `execute()`            | 행 단위 결과가 필요할 때 사용        |
| `scalars()`            | ORM 객체나 단일 값 목록을 얻을 때 사용 |
| `get()`                | 기본 키로 객체 하나를 조회할 때 사용    |
| `scalar_one_or_none()` | 결과가 없거나 정확히 하나여야 할 때 사용  |

## 11. 요청마다 Session을 분리하는 이유

Session은 현재 트랜잭션과 ORM 객체의 상태를 함께 관리함.

모든 HTTP 요청이 하나의 Session을 공유하면 다음 문제가 발생할 수 있음.

* 요청 A와 요청 B의 트랜잭션이 섞일 수 있음
* 한 요청의 rollback이 다른 요청에 영향을 줄 수 있음
* 서로 다른 요청이 같은 ORM 객체 상태를 공유할 수 있음
* 동시에 Session을 사용해 예측하기 어려운 오류가 발생할 수 있음

권장 구조는 다음과 같음.

```text
요청 A
→ Session A 생성
→ 데이터베이스 작업
→ commit 또는 rollback
→ Session A 종료

요청 B
→ Session B 생성
→ 데이터베이스 작업
→ commit 또는 rollback
→ Session B 종료
```

FastAPI에서는 Dependency를 이용해 요청마다 Session을 생성함.

```text
HTTP 요청 시작
→ get_db() 실행
→ Session 생성
→ 경로 함수에 Session 전달
→ 요청 처리
→ finally에서 Session 종료
```

Engine과 `sessionmaker`는 애플리케이션 전체에서 재사용하지만, 실제 Session 객체는 요청마다 새로 생성하는 구조임.

```text
Engine
→ 애플리케이션 전체에서 하나

SessionLocal
→ Session을 만드는 factory

Session 객체
→ HTTP 요청마다 하나
```

## 12. Pydantic Model과 ORM Model

두 모델은 모두 Python 클래스로 작성되지만 역할이 다름.

| 구분     | Pydantic Model  | SQLAlchemy ORM Model |
| ------ | --------------- | -------------------- |
| 사용 위치  | API 요청과 응답      | 데이터베이스 작업            |
| 주요 역할  | JSON 구조와 값 검증   | 클래스와 테이블 매핑          |
| 기반 클래스 | `BaseModel`     | `DeclarativeBase`    |
| 데이터 저장 | 직접 저장하지 않음      | Session을 통해 저장       |
| 표현 대상  | 클라이언트와 주고받는 데이터 | 데이터베이스 테이블과 행        |

처리 흐름은 다음과 같음.

```text
클라이언트 JSON 요청
→ Pydantic 요청 모델로 검증
→ SQLAlchemy ORM 객체 생성 또는 수정
→ Session
→ MySQL에 저장
```

조회 결과는 반대 순서로 응답됨.

```text
MySQL의 데이터 행
→ SQLAlchemy ORM 객체
→ Pydantic 응답 모델
→ JSON 응답
```

Pydantic 모델과 ORM 모델을 분리하면 API에서 허용할 데이터와 데이터베이스에 저장할 데이터를 서로 다르게 구성할 수 있음.

예를 들어 데이터베이스 모델에는 다음 필드가 있을 수 있음.

```text
id
title
completed
created_at
updated_at
deleted_at
internal_status
```

하지만 클라이언트 응답에는 일부 필드만 노출할 수 있음.

```text
id
title
completed
```

## 13. ForeignKey와 Relationship

ORM은 단일 테이블뿐 아니라 테이블 간 관계도 Python 객체 관계로 표현할 수 있음.

예를 들어 사용자 한 명이 여러 Task를 가질 수 있다고 가정함.

```text
users
├── id
└── name

tasks
├── id
├── title
└── user_id → users.id
```

이 관계는 일대다 관계임.

```text
User 1명
→ Task 여러 개
```

SQLAlchemy에서는 주로 `ForeignKey`와 `relationship()`을 사용함.

| 구성               | 역할                       |
| ---------------- | ------------------------ |
| `ForeignKey`     | 실제 데이터베이스 외래 키를 설정함      |
| `relationship()` | Python 객체 사이의 탐색 관계를 설정함 |

`ForeignKey`는 데이터베이스 차원의 관계임.

```text
tasks.user_id
→ users.id 참조
```

`relationship()`은 Python 객체에서 관련 데이터를 편리하게 사용할 수 있도록 함.

```text
user.tasks
→ 사용자가 가진 Task 목록

task.user
→ Task를 소유한 사용자
```

중요한 점은 `relationship()`만 작성한다고 실제 외래 키 컬럼이 만들어지는 것은 아니라는 점임.

```text
ForeignKey
→ DB 테이블 관계

relationship()
→ ORM 객체 관계
```

## 14. Lazy Loading과 N+1 문제

ORM 관계를 사용할 때는 실제로 어떤 SQL이 실행되는지 확인해야 함.

예를 들어 사용자 10명을 조회한 뒤 각 사용자의 Task 목록에 접근한다고 가정함.

```text
사용자 전체 조회
→ SELECT 1번

첫 번째 사용자의 tasks 조회
→ SELECT 1번

두 번째 사용자의 tasks 조회
→ SELECT 1번

...

열 번째 사용자의 tasks 조회
→ SELECT 1번
```

결과적으로 다음과 같이 총 11번의 SQL이 실행될 수 있음.

```text
사용자 조회 1번
+ 사용자별 Task 조회 10번
= 총 11번
```

이처럼 처음 조회한 데이터 N개에 대해 추가 쿼리가 각각 실행되는 문제를 **N+1 문제**라고 함.

N+1 문제는 ORM 코드만 보면 쉽게 드러나지 않을 수 있음.

```python
for user in users:
    print(user.tasks)
```

코드는 단순하지만 `user.tasks`에 접근할 때마다 SELECT가 실행될 가능성이 있음.

따라서 ORM을 사용할 때는 다음을 확인해야 함.

* 관계 속성 접근 시 추가 SQL이 실행되는지
* 몇 번의 SELECT가 발생하는지
* JOIN 또는 eager loading이 필요한지
* 조회할 데이터 범위가 적절한지

학습 단계에서는 `create_engine()`의 `echo=True`를 사용해 SQL 로그를 확인하는 것이 도움이 됨.

```text
ORM 코드 작성
→ 터미널의 SQL 로그 확인
→ 예상한 SQL과 실제 SQL 비교
```

## 15. 동기와 비동기 SQLAlchemy

이번 실습은 동기 방식으로 구성함.

```text
PyMySQL
→ 동기 Driver

Session
→ 동기 Session

FastAPI 경로 함수
→ def
```

비동기 SQLAlchemy를 사용하려면 일부 구성요소를 함께 변경해야 함.

```text
asyncmy 또는 aiomysql
→ 비동기 Driver

AsyncEngine
→ 비동기 Engine

AsyncSession
→ 비동기 Session

FastAPI 경로 함수
→ async def
```

경로 함수만 `async def`로 변경한다고 데이터베이스 작업이 자동으로 비동기가 되는 것은 아님.

```text
동기 Driver + 동기 Session
→ 동기 DB 작업

비동기 Driver + AsyncSession + await
→ 비동기 DB 작업
```

초기에는 동기 Session 구조를 먼저 정확하게 이해하고 이후 AsyncSession으로 확장하는 것이 적절함.

## 16. 전체 요청 처리 흐름

Task 생성 요청의 전체 흐름은 다음과 같음.

```text
1. 클라이언트가 JSON 요청 전송
2. FastAPI가 요청 수신
3. Pydantic이 요청 데이터 검증
4. Task ORM 객체 생성
5. Session.add()로 저장 대상 등록
6. commit 과정에서 INSERT 실행
7. Engine이 Connection 제공
8. PyMySQL이 MySQL에 SQL 전달
9. MySQL이 데이터 저장
10. ORM 객체를 Pydantic 응답 모델로 변환
11. JSON 응답 반환
```

구조로 표현하면 다음과 같음.

```text
클라이언트
→ FastAPI
→ Pydantic
→ SQLAlchemy ORM Model
→ Session
→ Engine
→ Connection Pool
→ MySQL Dialect
→ PyMySQL
→ MySQL
```

조회 결과는 반대 방향으로 돌아옴.

```text
MySQL의 행
→ PyMySQL
→ SQLAlchemy
→ ORM 객체
→ Pydantic
→ JSON 응답
→ 클라이언트
```

| ---------------- | ------------------------------ |
| ORM              | 테이블과 Python 클래스를 연결하는 방식       |

| SQLAlchemy Core  | SQL, 연결, 트랜잭션을 담당하는 기반 계층      |
| Engine           | DB 접속 설정과 Connection Pool을 관리함 |
| Dialect          | DBMS별 SQL 차이를 처리함              |
| Driver           | 데이터베이스와 실제 통신함                 |
| ORM Model        | 데이터베이스 테이블에 대응하는 클래스           |
| MetaData         | 등록된 테이블과 컬럼 구조 정보              |
| Session          | ORM 객체 상태와 트랜잭션을 관리함           |
| `add()`          | 새 객체를 Session에 등록함             |
| `flush()`        | 변경사항을 SQL로 전송함                 |
| `commit()`       | 트랜잭션을 확정함                      |
| `rollback()`     | 현재 트랜잭션의 변경을 취소함               |
| `refresh()`      | DB 값을 ORM 객체에 다시 반영함           |
| Unit of Work     | 객체 변경을 추적해 필요한 SQL을 결정함        |
| Identity Map     | 같은 기본 키를 하나의 객체로 관리함           |
| `select()`       | SELECT 문을 구성함                  |
| `scalars()`      | 실행 결과에서 ORM 객체를 추출함            |
| `get()`          | 기본 키로 객체 하나를 조회함               |
| `ForeignKey`     | 실제 DB 테이블 간 관계를 설정함            |
| `relationship()` | Python 객체 간 관계를 설정함            |
| N+1 문제           | 관계 데이터 조회로 SQL이 반복 실행되는 문제     |

```text
FastAPI
→ Pydantic
→ SQLAlchemy ORM
→ Session
→ Engine
→ Driver
→ MySQL
```

ORM을 사용할 때 가장 중요한 점은 Python 코드만 보는 것이 아니라 실제로 생성되는 SQL과 트랜잭션 범위를 함께 확인하는 것임.
