MySQL을 이용해 관계형 데이터베이스의 기본 개념을 이해하고, Task 프로젝트의 데이터베이스를 직접 설계하는 과정 정리

## 1. 데이터베이스가 필요한 이유

이전 Task CRUD 실습에서는 Python 딕셔너리를 데이터 저장소로 사용함

```python
tasks: dict[int, TaskResponse] = {}
```

데이터 저장 예시

```python
tasks[1] = TaskResponse(
    id=1,
    title="FastAPI 공부하기",
    description="CRUD API 구현",
    completed=False,
)
```

이 방식은 데이터를 간단하게 저장할 수 있지만 다음과 같은 문제가 존재함

| 문제             | 설명                          |
| -------------- | --------------------------- |
| 서버 종료 시 데이터 삭제 | 데이터가 메모리에만 존재함              |
| 여러 서버에서 공유 불가  | 각 서버가 서로 다른 딕셔너리를 사용함       |
| 복잡한 검색 어려움     | 정렬, 집계, 관계 조회 등을 직접 구현해야 함  |
| 데이터 무결성 보장 어려움 | 중복값과 잘못된 데이터 저장을 직접 검사해야 함  |
| 대량 데이터 처리 어려움  | 데이터가 많아질수록 메모리와 검색 성능 문제 발생 |

실제 서비스에서는 데이터를 계속 보관할 수 있는 데이터베이스 사용이 필요함

```text
클라이언트
→ FastAPI
→ MySQL
→ 데이터 저장
```

서버가 종료되더라도 MySQL에 저장된 데이터는 유지됨

## 2. 데이터베이스란

데이터를 일정한 구조로 저장하고 관리하는 시스템

예시

* 사용자 정보 저장
* 게시글 저장
* 상품과 주문 정보 저장
* 할 일 목록 저장
* 로그인 정보 저장

Task 데이터 예시

```text
1번 | FastAPI 공부하기 | 완료
2번 | MySQL 공부하기   | 미완료
3번 | 프로젝트 설계하기 | 미완료
```

데이터베이스를 사용하면 다음 작업 수행 가능함

```text
데이터 생성
데이터 조회
데이터 수정
데이터 삭제
검색
정렬
통계 계산
데이터 간 관계 연결
```

## 3. DB와 DBMS

### DB (Database)

실제로 저장된 데이터의 집합

```text
backend_study 데이터베이스
shopping_mall 데이터베이스
company 데이터베이스
```

### DBMS (Database Management System)

데이터베이스를 생성하고 관리하는 프로그램

| DBMS                 | 특징                       |
| -------------------- | ------------------------ |
| MySQL                | 웹 서비스에서 널리 사용되는 관계형 DBMS |
| PostgreSQL           | 복잡한 기능과 표준 SQL 지원이 강력함   |
| Oracle Database      | 대규모 기업 시스템에서 많이 사용됨      |
| Microsoft SQL Server | Microsoft 환경에서 많이 사용됨    |
| SQLite               | 별도 서버 없이 파일 하나로 동작함      |

MySQL은 데이터 자체가 아니라 **데이터를 관리하는 DBMS**임

```text
MySQL 프로그램
└── backend_study 데이터베이스
    ├── users 테이블
    └── tasks 테이블
```

## 4. 관계형 데이터베이스

관계형 데이터베이스는 데이터를 표 형태의 테이블로 저장하고, 테이블 사이의 관계를 이용해 데이터를 관리하는 방식임

영어로 `Relational Database`라고 하며 줄여서 `RDB`라고 표현함

관계형 데이터베이스를 관리하는 프로그램은 `RDBMS`라고 표현함

MySQL은 대표적인 RDBMS임

### 테이블 예시

`tasks` 테이블

| id | title        | description | completed |
| -: | ------------ | ----------- | --------- |
|  1 | FastAPI 공부하기 | CRUD 구현     | 1         |
|  2 | MySQL 공부하기   | SQL 연습      | 0         |
|  3 | 프로젝트 설계하기    | DB 구조 작성    | 0         |

테이블은 행과 열로 구성됨

| 용어     | 의미                 | 예시                   |
| ------ | ------------------ | -------------------- |
| Table  | 같은 종류의 데이터를 저장하는 표 | `tasks`              |
| Column | 데이터의 속성            | `title`, `completed` |
| Row    | 하나의 실제 데이터         | 1번 Task              |
| Field  | 특정 행의 특정 열 값       | `"MySQL 공부하기"`       |

## 5. MySQL 서버와 클라이언트

MySQL을 사용할 때는 서버와 클라이언트를 구분해야 함

### MySQL Server

데이터를 실제로 저장하고 SQL을 **실행**하는 프로그램

주요 역할

* 데이터베이스 생성
* 테이블 생성
* 데이터 저장
* 데이터 검색
* 사용자 인증
* 접근 권한 관리

### MySQL Client

MySQL Server에 **명령을 보내는** 프로그램

대표적인 클라이언트

| 클라이언트                     | 특징                             |
| ------------------------- | ------------------------------ |
| MySQL Workbench           | 화면을 통해 SQL을 작성하고 결과 확인 가능      |
| MySQL Command Line Client | 터미널에서 SQL 실행                   |
| FastAPI                   | Python 라이브러리를 통해 MySQL에 SQL 전송 |
| DBeaver                   | 여러 종류의 데이터베이스를 관리할 수 있는 프로그램   |

전체 구조

```text
MySQL Workbench
        ↓ SQL
MySQL Server
        ↓
데이터베이스와 테이블
```

FastAPI 연결 이후 구조

```text
클라이언트 → HTTP 요청 → FastAPI
→ SQL 실행 요청 → MySQL Server → 결과 반환
→ FastAPI → HTTP 응답
```

## 6. SQL (Structured Query Language)

관계형 데이터베이스에 명령을 전달하기 위한 언어임

SQL을 이용해 다음과 같은 작업 수행 가능함

```sql
CREATE DATABASE backend_study

SELECT * FROM tasks

UPDATE tasks
SET completed = TRUE
WHERE id = 1;
```

앞에서 말한 MySQL은 **SQL이라는 언어를 이해하는 프로그램**임


### SQL 작성 규칙

SQL 명령어는 일반적으로 대소문자를 구분하지 않음

하지만, 가독성을 위해 SQL **명령어는 대문자**로, **테이블명과 컬럼명은 소문자**로 작성하는 방식이 많이 사용됨

```sql
SELECT title, completed
FROM tasks;
```
마지막엔 ;로 끝내야 함

## 7. SQL 명령어 종류

SQL 명령어는 역할에 따라 구분 가능함

| 구분  | 전체 이름                        | 역할             | 명령어                          |
| --- | ---------------------------- | -------------- | ---------------------------- |
| DDL | Data Definition Language     | 데이터 구조 정의      | `CREATE`, `ALTER`, `DROP`    |
| DML | Data Manipulation Language   | 데이터 추가, 수정, 삭제 | `INSERT`, `UPDATE`, `DELETE` |
| DQL | Data Query Language          | 데이터 조회         | `SELECT`                     |
| TCL | Transaction Control Language | 작업 확정 또는 취소    | `COMMIT`, `ROLLBACK`         |
| DCL | Data Control Language        | 권한 관리          | `GRANT`, `REVOKE`            |

처음에는 다음 다섯 가지 명령을 중심으로 학습함

```text
CREATE
INSERT
SELECT
UPDATE
DELETE
```

CRUD와 SQL의 관계

| CRUD   | SQL      |
| ------ | -------- |
| Create | `INSERT` |
| Read   | `SELECT` |
| Update | `UPDATE` |
| Delete | `DELETE` |

## 8. MySQL 접속

### MySQL Workbench 사용

MySQL 설치 시 MySQL Server와 MySQL Workbench를 함께 설치할 수 있음

접속 순서

```text
MySQL Server 실행
→ MySQL Workbench 실행
→ Local instance 선택
→ 비밀번호 입력
→ SQL 작성 화면 접속
```

SQL 작성 후 번개 모양 실행 버튼을 누르면 SQL 실행됨

여러 SQL 중 특정 문장만 실행하려면 해당 문장을 선택한 뒤 실행함

### 터미널 사용

```bash
mysql -u root -p
```

| 부분        | 의미             |
| --------- | -------------- |
| `mysql`   | MySQL 클라이언트 실행 |
| `-u root` | `root` 사용자로 접속 |
| `-p`      | 비밀번호 입력        |

접속 후 비밀번호 입력

정상 접속 시 다음과 같은 프롬프트 표시

```text
mysql>
```

MySQL 종료

```sql
EXIT;
```

## 9. 데이터베이스 생성

현재 MySQL Server에 존재하는 데이터베이스 확인

```sql
SHOW DATABASES;
```

프로젝트에서 사용할 데이터베이스 생성

```sql
CREATE DATABASE backend_study;
```

한글과 이모지 등을 안전하게 저장하기 위한 문자 설정 포함

```sql
CREATE DATABASE backend_study
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;
```

| 설정                   | 의미                             |
| -------------------- | ------------------------------ |
| `utf8mb4`            | 한글, 영문, 이모지 등을 저장할 수 있는 문자 인코딩 |
| `utf8mb4_unicode_ci` | 문자 비교와 정렬에 사용하는 규칙             |

데이터베이스 생성 확인

```sql
SHOW DATABASES;
```

사용할 데이터베이스 선택

```sql
USE backend_study;
```

현재 선택한 데이터베이스 확인

```sql
SELECT DATABASE();
```

예상 결과

```text
backend_study
```

## 10. 테이블 설계

테이블을 생성하기 전에 어떤 데이터를 저장할지 먼저 결정해야 함

Task 프로젝트 요구사항

* 사용자를 저장해야 함
* 한 사용자가 여러 Task를 생성할 수 있음
* Task 제목과 설명을 저장해야 함
* Task 완료 여부를 저장해야 함
* 생성 시각과 수정 시각을 저장해야 함

필요한 테이블

```text
users
tasks
```

### users 테이블

| 컬럼           | 타입     | 설명        |
| ------------ | ------ | --------- |
| `id`         | 정수     | 사용자 고유 번호 |
| `name`       | 문자열    | 사용자 이름    |
| `email`      | 문자열    | 사용자 이메일   |
| `created_at` | 날짜와 시간 | 사용자 생성 시각 |

### tasks 테이블

| 컬럼            | 타입     | 설명              |
| ------------- | ------ | --------------- |
| `id`          | 정수     | Task 고유 번호      |
| `user_id`     | 정수     | Task를 만든 사용자 번호 |
| `title`       | 문자열    | Task 제목         |
| `description` | 문자열    | Task 설명         |
| `completed`   | 참·거짓   | 완료 여부           |
| `created_at`  | 날짜와 시간 | 생성 시각           |
| `updated_at`  | 날짜와 시간 | 수정 시각           |

## 11. 데이터 타입

MySQL에서는 각 컬럼에 저장할 데이터 타입을 미리 지정함

| 타입           | 용도             | 예시                    |
| ------------ | -------------- | --------------------- |
| `INT`        | 일반적인 정수        | 나이, 수량                |
| `BIGINT`     | 큰 범위의 정수       | ID                    |
| `VARCHAR(n)` | 최대 길이가 정해진 문자열 | 이름, 제목, 이메일           |
| `TEXT`       | 길이가 긴 문자열      | 게시글 본문                |
| `BOOLEAN`    | 참 또는 거짓        | 완료 여부                 |
| `DATE`       | 날짜             | `2026-07-19`          |
| `DATETIME`   | 날짜와 시간         | `2026-07-19 10:30:00` |
| `TIMESTAMP`  | 날짜와 시간         | 생성 시각, 수정 시각          |
| `DECIMAL`    | 정확한 소수         | 상품 가격, 금액             |
| `FLOAT`      | 근삿값 소수         | 측정값                   |

### VARCHAR와 TEXT

```sql
title VARCHAR(100)
```

최대 100자의 문자열 저장 가능함

```sql
description TEXT
```

상대적으로 긴 문자열 저장에 적합함

길이가 제한된 제목과 이메일에는 `VARCHAR` 사용이 적합함

게시글 본문과 같이 길이가 긴 데이터에는 `TEXT` 사용이 적합함

### BOOLEAN

MySQL에서 `BOOLEAN`은 내부적으로 `TINYINT(1)` 형태로 처리됨

FALSE 대신 0을, TRUE 대신 1을 써도 문제 없음

```text
FALSE → 0
TRUE  → 1
```

## 12. NULL과 빈 문자열

`NULL`은 값이 존재하지 않음을 의미함

```text
description = NULL
```

빈 문자열은 문자열 값이 존재하지만 내용이 비어 있음을 의미함

```text
description = ""
```

두 값은 서로 다름

| 값      | 의미             |
| ------ | -------------- |
| `NULL` | 값 자체가 없음       |
| `''`   | 길이가 0인 문자열이 있음 |

NULL 검색 시 `=` 대신 `IS NULL` 사용

```sql
SELECT *
FROM tasks
WHERE description IS NULL;
```

NULL이 아닌 데이터 검색

```sql
SELECT *
FROM tasks
WHERE description IS NOT NULL;
```

## 13. 제약 조건

제약 조건은 잘못된 데이터가 저장되지 않도록 제한하는 규칙임

| 제약 조건         | 의미                 |
| ------------- | ------------------ |
| `PRIMARY KEY` | 각 행을 고유하게 식별       |
| `FOREIGN KEY` | 다른 테이블의 행을 참조      |
| `NOT NULL`    | NULL 저장 금지         |
| `UNIQUE`      | 중복값 저장 금지          |
| `DEFAULT`     | 값을 생략했을 때 기본값 적용   |
| `CHECK`       | 값이 특정 조건을 만족하는지 확인 |

### PRIMARY KEY

각 행을 구분하는 고유한 값

```sql
id BIGINT PRIMARY KEY
```

Primary Key는 다음 조건을 만족해야 함

* 중복 불가
* NULL 불가
* 하나의 행을 정확히 식별 가능

### AUTO_INCREMENT

새로운 행이 추가될 때 ID를 자동으로 증가시킴

```sql
id BIGINT AUTO_INCREMENT PRIMARY KEY
```

데이터 추가 결과

```text
첫 번째 사용자 → id 1
두 번째 사용자 → id 2
세 번째 사용자 → id 3
```

### NOT NULL

반드시 값이 존재해야 하는 컬럼

```sql
title VARCHAR(100) NOT NULL
```

제목 없이 Task를 저장할 수 없도록 제한함

### UNIQUE

같은 값을 중복 저장할 수 없도록 제한함

```sql
email VARCHAR(255) NOT NULL UNIQUE
```

동일한 이메일로 여러 사용자를 생성할 수 없도록 함

### DEFAULT

값을 전달하지 않았을 때 적용되는 기본값

```sql
completed BOOLEAN NOT NULL DEFAULT FALSE
```

`completed`를 생략하면 자동으로 `FALSE` 저장됨

## 14. 테이블 관계

관계형 데이터베이스에서는 여러 테이블을 관계로 연결함

### 일대일 관계

한 행이 다른 테이블의 한 행과 연결되는 관계

```text
사용자 1명 ↔ 사용자 프로필 1개
```

### 일대다 관계

한 행이 다른 테이블의 여러 행과 연결되는 관계

```text
사용자 1명 → 여러 Task
```

```text
users
id: 1, name: Kim

tasks
id: 1, user_id: 1
id: 2, user_id: 1
id: 3, user_id: 1
```

한 사용자가 여러 Task를 가지므로 `users`와 `tasks`는 일대다 관계임

### 다대다 관계

여러 행이 서로 여러 행과 연결되는 관계

```text
학생 여러 명 ↔ 강의 여러 개
```

다대다 관계는 중간 테이블을 만들어 표현함

```text
students
courses
student_courses
```

Task에 여러 태그를 연결하는 경우

```text
tasks
tags
task_tags
```

## 15. Primary Key와 Foreign Key

### Primary Key

현재 테이블에서 행을 고유하게 구분하는 값

```text
users.id
tasks.id
```

### Foreign Key

다른 테이블의 Primary Key를 참조하는 값

```text
tasks.user_id → users.id
```

관계 표현

```text
users
┌────┬──────┐
│ id │ name │
├────┼──────┤
│ 1  │ Kim  │
└────┴──────┘
       ↑
       │ tasks.user_id
       │
tasks
┌────┬─────────┬──────────────────┐
│ id │ user_id │ title            │
├────┼─────────┼──────────────────┤
│ 1  │ 1       │ FastAPI 공부하기 │
│ 2  │ 1       │ MySQL 공부하기   │
└────┴─────────┴──────────────────┘
```

존재하지 않는 사용자 번호가 Task에 저장되지 않도록 Foreign Key로 제한 가능함

```text
users에 id 100이 없음
→ tasks.user_id에 100 저장 불가
```

## 16. users 테이블 생성

```sql
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

컬럼별 의미

| 선언                  | 의미             |
| ------------------- | -------------- |
| `id BIGINT`         | 큰 범위의 정수       |
| `UNSIGNED`          | 음수 사용 불가       |
| `AUTO_INCREMENT`    | ID 자동 증가       |
| `PRIMARY KEY`       | 사용자를 고유하게 식별   |
| `name VARCHAR(50)`  | 최대 50자의 사용자 이름 |
| `NOT NULL`          | 값 생략 불가        |
| `email UNIQUE`      | 이메일 중복 불가      |
| `CURRENT_TIMESTAMP` | 현재 시각 자동 저장    |

## 17. tasks 테이블 생성

```sql
CREATE TABLE tasks (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    title VARCHAR(100) NOT NULL,
    description VARCHAR(500) NULL,
    completed BOOLEAN NOT NULL DEFAULT FALSE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL
        DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    CONSTRAINT fk_tasks_user
        FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
);
```

### Foreign Key 설정

```sql
FOREIGN KEY (user_id)
REFERENCES users(id)
```

`tasks.user_id`가 `users.id`를 참조함

참조되는 컬럼과 참조하는 컬럼의 타입은 동일하게 맞추는 것이 중요함

```text
users.id     → BIGINT UNSIGNED
tasks.user_id → BIGINT UNSIGNED
```

### ON DELETE CASCADE

사용자가 삭제되면 해당 사용자의 Task도 함께 삭제됨

```text
users의 id 1 삭제
→ user_id가 1인 tasks도 자동 삭제
```

편리하지만 실제 프로젝트에서는 데이터 삭제 정책을 고려해 선택해야 함

사용자를 삭제해도 Task를 유지해야 한다면 다른 방식이 필요함

## 28. JOIN: 관련 테이블 함께 조회

`tasks` 테이블에는 사용자의 이름과 이메일이 저장되어 있지 않음

```text
tasks.user_id
```

사용자 정보는 `users` 테이블에 저장되어 있음

두 테이블의 데이터를 함께 확인하려면 `JOIN` 사용함

### INNER JOIN

사용자가 존재하는 Task만 조회

```sql
SELECT
    tasks.id,
    tasks.title,
    tasks.completed,
    users.id AS user_id,
    users.name AS user_name,
    users.email
FROM tasks
INNER JOIN users
    ON tasks.user_id = users.id;
```

연결 조건

```sql
tasks.user_id = users.id
```

결과 예시

| id | title        | completed | user_id | user_name | email                                     |
| -: | ------------ | --------: | ------: | --------- | ----------------------------------------- |
|  1 | FastAPI 공부하기 |         1 |       1 | Kim       | [kim@example.com](mailto:kim@example.com) |
|  2 | MySQL 공부하기   |         0 |       1 | Kim       | [kim@example.com](mailto:kim@example.com) |

### 테이블 별칭 사용

```sql
SELECT
    t.id,
    t.title,
    t.completed,
    u.name AS user_name,
    u.email
FROM tasks AS t
INNER JOIN users AS u
    ON t.user_id = u.id;
```

| 별칭  | 테이블     |
| --- | ------- |
| `t` | `tasks` |
| `u` | `users` |

테이블 이름이 길거나 여러 테이블을 연결할 때 유용함

### LEFT JOIN

Task가 없는 사용자도 함께 조회

```sql
SELECT
    u.id,
    u.name,
    t.title
FROM users AS u
LEFT JOIN tasks AS t
    ON u.id = t.user_id;
```

| JOIN         | 결과                         |
| ------------ | -------------------------- |
| `INNER JOIN` | 양쪽 테이블에 모두 일치하는 데이터        |
| `LEFT JOIN`  | 왼쪽 테이블은 모두 포함하고 오른쪽 데이터 연결 |

## 30. GROUP BY

같은 값을 가진 행을 그룹으로 묶어 집계함

사용자별 Task 개수

```sql
SELECT
    user_id,
    COUNT(*) AS task_count
FROM tasks
GROUP BY user_id;
```

사용자 이름까지 함께 조회

```sql
SELECT
    u.id,
    u.name,
    COUNT(t.id) AS task_count
FROM users AS u
LEFT JOIN tasks AS t
    ON u.id = t.user_id
GROUP BY
    u.id,
    u.name;
```

결과 예시

| id | name | task_count |
| -: | ---- | ---------: |
|  1 | Kim  |          2 |
|  2 | Lee  |          1 |
|  3 | Park |          0 |

### HAVING

그룹화한 결과에 조건을 적용함

Task가 2개 이상인 사용자 조회

```sql
SELECT
    user_id,
    COUNT(*) AS task_count
FROM tasks
GROUP BY user_id
HAVING COUNT(*) >= 2;
```

| 구문       | 적용 대상       |
| -------- | ----------- |
| `WHERE`  | 그룹화 전 개별 행  |
| `HAVING` | 그룹화 후 집계 결과 |

## 31. SELECT문의 논리적 처리 순서

SQL을 작성하는 순서

```sql
SELECT
FROM
WHERE
GROUP BY
HAVING
ORDER BY
LIMIT
```

데이터베이스가 개념적으로 처리하는 순서

```text
FROM
→ WHERE
→ GROUP BY
→ HAVING
→ SELECT
→ ORDER BY
→ LIMIT
```

예시

```sql
SELECT
    user_id,
    COUNT(*) AS task_count
FROM tasks
WHERE completed = FALSE
GROUP BY user_id
HAVING COUNT(*) >= 2
ORDER BY task_count DESC
LIMIT 5;
```

처리 흐름

```text
tasks 테이블 확인
→ 미완료 Task만 선택
→ 사용자별 그룹 생성
→ Task가 2개 이상인 그룹 선택
→ user_id와 개수 생성
→ 개수 내림차순 정렬
→ 최대 5개 반환
```

## 33. 데이터 무결성

데이터 무결성은 데이터가 정확하고 일관된 상태를 유지하는 것을 의미함

### 개체 무결성

각 행을 Primary Key로 고유하게 식별해야 함

```text
users.id 중복 불가
tasks.id 중복 불가
```

### 참조 무결성

Foreign Key가 참조하는 데이터가 실제로 존재해야 함

```text
tasks.user_id = 10
→ users.id = 10이 존재해야 함
```

### 도메인 무결성

컬럼에 저장되는 값이 정해진 타입과 조건을 따라야 함

```text
completed → 참 또는 거짓
title → NULL 불가
email → 중복 불가
```

## 34. 정규화 기초

정규화는 중복 데이터를 줄이고 데이터 변경 시 발생할 수 있는 문제를 방지하도록 테이블을 나누는 과정임

잘못된 테이블 구조 예시

| task_id | title      | user_name | user_email                                |
| ------: | ---------- | --------- | ----------------------------------------- |
|       1 | FastAPI 공부 | Kim       | [kim@example.com](mailto:kim@example.com) |
|       2 | MySQL 공부   | Kim       | [kim@example.com](mailto:kim@example.com) |
|       3 | Docker 공부  | Kim       | [kim@example.com](mailto:kim@example.com) |

같은 사용자 정보가 반복됨

사용자 이메일이 변경되면 여러 행을 모두 수정해야 함

```text
kim@example.com
→ kim2@example.com
```

테이블 분리

`users`

| id | name | email                                     |
| -: | ---- | ----------------------------------------- |
|  1 | Kim  | [kim@example.com](mailto:kim@example.com) |

`tasks`

| id | user_id | title      |
| -: | ------: | ---------- |
|  1 |       1 | FastAPI 공부 |
|  2 |       1 | MySQL 공부   |
|  3 |       1 | Docker 공부  |

사용자 정보는 한 번만 저장하고 Task에서는 `user_id`만 저장함

장점

* 중복 데이터 감소
* 데이터 수정 범위 감소
* 데이터 일관성 향상
* 테이블 역할 명확화

모든 데이터를 무조건 세분화하는 것이 목적은 아님

프로젝트 요구사항과 조회 성능을 함께 고려해야 함

## 35. 인덱스 기초

인덱스는 데이터 검색 속도를 높이기 위한 별도의 자료 구조임

책의 목차나 색인과 비슷한 역할임

다음 조건으로 자주 검색하는 경우 인덱스를 고려할 수 있음

```sql
SELECT *
FROM tasks
WHERE user_id = 1;
```

인덱스 생성

```sql
CREATE INDEX idx_tasks_user_id
ON tasks(user_id);
```

완료 여부와 사용자 번호를 함께 검색하는 경우

```sql
CREATE INDEX idx_tasks_user_completed
ON tasks(user_id, completed);
```

Primary Key와 Unique 컬럼에는 일반적으로 인덱스가 자동 생성됨

인덱스는 조회 속도를 높일 수 있지만 다음 비용이 발생함

* 추가 저장 공간 필요
* INSERT 속도 저하 가능
* UPDATE 속도 저하 가능
* DELETE 속도 저하 가능

모든 컬럼에 인덱스를 만드는 방식은 적절하지 않음

실제 조회 조건을 기준으로 설계해야 함

## 37. 파이썬에서 SQL 쿼리 없이 DB와 통신하는 법: ORM

방금 본 HTTP와 SQL 연결은 FastAPI의 경우 파이썬으로 이뤄질텐데, 무식한 방법으론 들어올 수 있는 모든 입력을 SQL로 변환하는 코드를 짜야 함

하지만, 당연히 그럴 필요는 없고 파이썬에는 SQL을 자동으로 생성해 주는 **ORM(Object-Relational Mapping)** 라이브러리가 존재함

### ORM(Object-Relational Mapping)이란?

데이터베이스의 '테이블'을 파이썬의 '클래스(Class)'로, 테이블 안의 '데이터(Row)'를 파이썬의 '객체(Object)'로 매핑(연결)해 주는 기술

이를 사용하면 텍스트 형태의 쿼리문(Raw SQL)을 작성하는 대신, 우리에게 익숙한 **파이썬 객체 지향 코드**로 데이터베이스를 제어할 수 있음

> **대표적인 파이썬 ORM:** `SQLAlchemy`, `Django ORM`, `SQLModel`

---

### 코드 비교: Raw SQL vs ORM

**1. Raw SQL**

매번 쿼리문을 문자열로 작성해야 함. 하기 싫어짐

```python
# 직접 SQL 쿼리를 작성하여 실행
sql = "INSERT INTO tasks (user_id, title, description) VALUES (%s, %s, %s)"
cursor.execute(sql, (1, "MySQL 공부하기", "SQL 문법 연습"))
```

**2. ORM**

파이썬 객체를 만들고 DB 세션에 추가(`add`)만 하면, 라이브러리가 알아서 안전한 SQL 문으로 번역하여 DB에 전달

```python
# 1. 파이썬 객체 생성
new_task = Task(user_id=1, title="MySQL 공부하기", description="SQL 문법 연습")

# 2. DB에 추가 (내부적으로 SQL이 자동 생성되어 실행됨)
session.add(new_task)
session.commit()
```

---

### ORM 장점

1. **생산성 향상:** SQL 문법을 일일이 타이핑할 필요 없이 파이썬 코드만으로 빠르게 기능을 개발 가능
2. **가독성 및 유지보수:** 코드가 직관적이며, 테이블 구조가 변경되어도 파이썬 클래스만 수정하면 됨
3. **보안 강화:** 개발자가 쿼리를 직접 조작하면서 발생할 수 있는 보안 위협(SQL 인젝션 등)을 라이브러리가 알아서 방어해줌
4. **DB 독립성:** 향후 MySQL에서 PostgreSQL 등으로 데이터베이스 종류를 바꾸더라도 파이썬 코드를 거의 수정할 필요가 없음

## 38. SQL Injection 주의

사용자 입력을 SQL 문자열에 직접 붙이면 보안 문제가 발생할 수 있음

잘못된 방식

```python
sql = f"""
SELECT *
FROM users
WHERE email = '{email}'
"""
```

악의적인 입력이 SQL 구조를 변경할 수 있음

실제 FastAPI 연결 시 다음 방식 사용 필요함

* 파라미터 바인딩 사용
* SQLAlchemy와 같은 ORM 사용
* 사용자 입력을 SQL 문자열에 직접 연결하지 않음

안전한 방식의 개념

```python
cursor.execute(
    "SELECT * FROM users WHERE email = %s",
    (email,),
)
```

값과 SQL 문장을 분리해 전달함

## 43. DROP과 DELETE 차이

```sql
DELETE FROM tasks;
```

### DROP TABLE

테이블 구조와 데이터 모두 삭제함

```sql
DROP TABLE tasks;
```

### DROP DATABASE

데이터베이스 전체 삭제

```sql
DROP DATABASE backend_study;
```

삭제된 데이터는 복구하기 어려울 수 있으므로 주의 필요함

| 명령어             | 삭제 대상       |
| --------------- | ----------- |
| `DELETE`        | 테이블의 행      |
| `DROP TABLE`    | 테이블 구조와 데이터 |
| `DROP DATABASE` | 데이터베이스 전체   |

```text
클라이언트

```
